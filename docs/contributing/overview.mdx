# Contributing to Tempest

This guide covers the Tempest project structure, development workflow, and how to extend the application with new features like agents, themes, and Tauri commands.

## Running the Dev Build

Prerequisites: Node.js 20+, Rust (latest stable via rustup), WebView2 Runtime (Windows only)

```bash
# Clone and install
git clone https://github.com/tempestai-dev/tempest
cd tempest
npm install

# Start dev build with hot reload
npm run dev
```

`npm install` runs the postinstall scripts, which stage the bundled sidecars into `src-tauri/resources/` (the Atlas runtime from the `@usetempest/atlas` package, the chat bridge Node dependencies) and fetch the `cloudflared` tunnel binary.

The dev command (`tauri dev`):
1. Starts the Vite dev server on http://localhost:1420
2. Launches the Tauri webview pointing at the dev server
3. Hot-reloads React/TypeScript changes; recompiles Rust when `src-tauri/` files change

The app opens in a frameless window with custom styling via Tauri's window configuration.

For frontend-only work without rebuilding Rust:

```bash
npm run dev:frontend
```

This starts the Vite dev server only. Changes to React/TypeScript hot-reload instantly.

## Production Build

```bash
npm run build:frontend  # Compile TypeScript and bundle with Vite
npm run build           # Build Rust binary and create installers
```

`npm run build` runs `tauri build` and then `scripts/collect-artifacts.mjs`. On a Windows machine it produces an NSIS installer, an MSI, and a portable `.exe`, copying the NSIS installer and the portable executable to `dist-installers/` alongside updater artifacts. The released macOS and Linux artifacts (`.dmg`/`.app.tar.gz`, `.AppImage`/`.deb`) are built by CI.

## Adding a New Agent

Agents are **manifest-driven**. The bundled list ships as `config/agents.json` (16 agents), is merged with a minisign-verified remote manifest fetched from this repository, and is further merged with user-added agents from **Settings → Agents**. `AGENT_CONFIGS` is derived from that manifest via `src/lib/agentRegistry.ts` — there is no hardcoded agent array to edit.

The full procedure — manifest entry shape, flag templates, placeholders, icon rules, and the validation checks — is documented in [Supported Agents](/agents/supported). The short version:

1. Add an entry to `config/agents.json` with the agent's `command`, flag templates (`flags.session`, `flags.resume`, `flags.model`, `flags.autoApprove`, `flags.print`), and optionally a `capture` spec for agents that print their own session ID.
2. Commit the icon to `config/agent-icons/` (bundled built-ins also live in `src/assets/agent-icons/`).
3. Verify each flag against the CLI's own `--help`, then run `npm test` — `src/lib/agentsManifestFile.check.ts` validates the shipped manifest (unique ids, resolvable icons, known placeholders).
4. New agent entries reach existing installs through the signed remote manifest once `config/agents.json.minisig` is regenerated; until then they ship with the next release's bundled floor.

## Adding a New Tauri Command

Tauri commands bridge the React frontend and Rust backend. They are called from TypeScript via `invoke()` and handled by `#[tauri::command]` functions in Rust.

### Example: Read a File

**Step 1: Add the Rust function** in `src-tauri/src/lib.rs`:

```rust
#[tauri::command]
fn read_file(path: String) -> Result<String, String> {
    std::fs::read_to_string(&path).map_err(|e| e.to_string())
}
```

Tauri automatically serializes the return type to JSON and deserializes errors.

**Step 2: Register the command** in the builder in `lib.rs`:

```rust
pub fn run() {
    tauri::Builder::default()
        .invoke_handler(tauri::generate_handler![
            create_workspace,
            list_directory,
            read_file,        // Add this
            write_file,
            // ... other commands
        ])
        // ... rest of builder
}
```

**Step 3: Call from React** in `src/components/MyComponent.tsx`:

```typescript
import { invoke } from "@tauri-apps/api/core";

async function handleClick() {
  try {
    const content = await invoke<string>("read_file", { path: "/path/to/file" });
    console.log(content);
  } catch (e) {
    console.error("Error:", e);
  }
}
```

### Tauri Command Patterns

**Returning data:**

```rust
#[tauri::command]
fn get_user_data() -> Result<UserData, String> {
    Ok(UserData { name: "Alice" })
}
```

Returns JSON-serializable types. Use `serde::Serialize` on structs.

**Taking parameters:**

```rust
#[tauri::command]
fn calculate(a: i32, b: i32) -> i32 {
    a + b
}
```

Function arguments are automatically deserialized from the invoke call's payload.

**Long-running commands with streaming:**

For long operations (like indexing files), use Tauri channels:

```rust
#[tauri::command]
async fn start_index(app: tauri::AppHandle, project_path: String) -> Result<(), String> {
    // Spawn background work
    tokio::spawn(async move {
        // Emit events back to frontend
        app.emit("index:progress", serde_json::json!({
            "path": project_path,
            "status": "done"
        }))?;
    });
    Ok(())
}
```

On the frontend, listen for events:

```typescript
import { listen } from "@tauri-apps/api/event";

const unlisten = await listen("index:progress", (event) => {
    console.log(event.payload);
});
```

## Code Patterns and Style

### React Components

Components use functional components with hooks:

```typescript
import { useState, useCallback } from "react";

export function MyComponent({ prop1, prop2 }: Props) {
  const [state, setState] = useState(false);

  const handleClick = useCallback(() => {
    setState(true);
  }, []);

  return (
    <div className="my-component">
      <button onClick={handleClick}>Click me</button>
      {state && <p>State is true</p>}
    </div>
  );
}
```

### CSS Variables for Theming

Always use CSS variables for colors and UI tokens. Never hardcode color values.

```css
.my-element {
  background: var(--tempest-bg-editor);
  color: var(--tempest-fg-default);
  border: 1px solid var(--tempest-border-default);
}

.my-element:hover {
  background: var(--tempest-bg-hover);
}
```

CSS variables follow the naming pattern: `--tempest-{token.with.dots}` becomes `--tempest-{token-with-dashes}`.

### Error Handling

Use Result types and bubble errors:

```typescript
async function loadProject(path: string) {
  try {
    const files = await invoke("list_directory", { path });
    return files;
  } catch (e) {
    console.error("Failed to load project:", e);
    throw e; // Re-throw if the caller should handle it
  }
}
```

### State Management

Tempest does not use Redux, Zustand, or Jotai. State lives in module-singleton stores under `src/store/` built on React's `useSyncExternalStore` — plain objects with getter/setter functions, plus `use*` hooks that subscribe with fine-grained selectors. The general shape:

```typescript
let value = 0;
const listeners = new Set<() => void>();

export function setValue(next: number) {
  value = next;
  listeners.forEach((l) => l());
}

export function getValue() {
  return value;
}

export function useValue(): number {
  return useSyncExternalStore(
    (onChange) => { listeners.add(onChange); return () => listeners.delete(onChange); },
    () => value
  );
}
```

Settings that must survive restarts are written through the runtime state layer (persisted to the SQLite `app_state` table) rather than held only in a store — see [State Management](/internals/state).

### TypeScript Types

Always define prop types and return types explicitly:

```typescript
interface MyComponentProps {
  title: string;
  count: number;
  onAction?: (id: string) => void;
}

export function MyComponent({ title, count, onAction }: MyComponentProps) {
  // ...
}
```

## Testing

Tempest uses lightweight self-checks rather than a test framework: assertions live as `src/**/*.check.ts` files that import pure functions and assert with `node:assert` (Node strips TS types natively). `tests/run.mjs` discovers every check file and runs each in its own Node process.

```bash
npm test                # Run all 18 check files
npm test agentManifest  # Run only checks whose path matches the filter
node tests/run.mjs -v   # Verbose stdout
```

There is no Vitest at the repo root (only the published Atlas package uses Vitest in its own repository) and no Rust integration-test directory. Manual testing via the dev build is still standard for UI work:

1. Run `npm run dev`
2. Interact with the feature in the app
3. Check the browser console (F12) for errors
4. Verify the expected behavior

If you add a pure function with edge cases, add a `.check.ts` beside it so `npm test` guards it.

For debugging:

- Use React DevTools browser extension to inspect component state
- Use the Tauri DevTools (right-click > Inspect) to see window/console output
- Add `console.log()` statements liberally

## Performance Considerations

### Large File Trees

The file tree in the right sidebar is lazy-loaded. Nested folders do not fetch contents until expanded. This keeps the sidebar responsive even in large monorepos.

### Git Status

Git status operations are debounced and only refresh the Changes tab, not the file tree. This prevents layout shifts while browsing.

### Terminal Rendering

The embedded xterm.js terminal uses WebGL acceleration when available (via `@xterm/addon-webgl`). The WebGL context is pooled to avoid creating too many contexts simultaneously.

### Code Editor

Syntax highlighting uses CodeMirror with language-specific tokenizers. Avoid rendering very large files (10k+ lines) in the editor at once.

## Debugging Tips

1. **Frontend logs** - Open DevTools (F12) and check the Console tab
2. **Tauri logs** - Right-click the Tempest window and select "Inspect" to see the native console
3. **React state** - Install React DevTools browser extension and inspect component props/state
4. **Network requests** - Check the Network tab for API calls (e.g., GitHub PR creation)
5. **Git operations** - Git commands are invoked via Tauri; check stderr for git error messages
