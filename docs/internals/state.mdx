## Overview

Tempest splits state between two layers:

- **React frontend** — UI state lives in 24 custom store modules under `src/store/`, all built on React's `useSyncExternalStore` hook. No Redux, Zustand, or Jotai.
- **Rust backend** — process management (PTY sessions, git operations, Docker isolation) lives in `src-tauri/`. The backend holds no persistent state of its own.

The two layers synchronize through Tauri IPC commands. Anything that must survive a restart is written to a SQLite database by the frontend through `db_*` commands. See [Tauri Commands](/internals/tauri-commands) for the full command reference.

## Persistence layer

All user-facing persistent state lives in a single SQLite database, `tempest.db`, inside the app data directory for the identifier `com.user.tempest`:

<Tabs>
  <Tab title="Windows">
    `%APPDATA%\com.user.tempest\tempest.db`
  </Tab>
  <Tab title="macOS">
    `~/Library/Application Support/com.user.tempest/tempest.db`
  </Tab>
  <Tab title="Linux">
    `~/.local/share/com.user.tempest/tempest.db`
  </Tab>
</Tabs>

The database has 16 tables:

| Table | Purpose |
|-------|---------|
| `projects` | Projects opened in the app, with per-project settings such as worktree order and the Token Intelligence index decision |
| `branches` | Git branches seen per project |
| `sessions` | Terminal and agent sessions, keyed to a project and (when applicable) a branch |
| `layouts` | One saved pane layout per project |
| `layout_nodes` | The split tree of a layout (`SPLIT` and `SESSION` nodes with direction, size, and order) |
| `recents` | Recently opened projects |
| `tabs` | Restored non-terminal tabs (`diff`, `preview`, `editor`, `thread`) |
| `app_state` | Key/value store for JSON blobs — user preferences live here under the key `runtime` |
| `threads` | Chat thread boards |
| `thread_nodes` | Nodes on a thread board, with position, size, and the session they reference |
| `thread_messages` | Messages within a thread |
| `thread_edges` | Connections between nodes on a thread board |
| `automations` | Automation definitions |
| `automation_runs` | Run history per automation |
| `automation_prompt_versions` | Versioned prompts saved per automation |
| `notes` | User notes (title, body, scope) |

Preferences are **not** a forest of files. They are a single JSON blob in `app_state` under the key `"runtime"`, read and written through the `db_load_app_state` and `db_set_app_state` commands and mirrored in `RuntimeState` (below).

### Other on-disk locations

Beyond the main database, a few pieces of state live outside it:

| Location | Contents |
|----------|----------|
| `~/.tempest/dbiso.db` | Bookkeeping for [Database Branches](/database-branches/overview) — Docker base images registered per workspace |
| `~/.tempest/hooks/` | Managed endpoint scripts for the agent lifecycle hooks |
| `<app-data>/atlas-daemons.json` | Persisted `project_path → pid` map so Atlas daemons can be found (and cleaned up) across restarts |
| OS keyring, service `tempest-byok` | Provider API keys and task-source credentials, stored via the OS credential vault — never in the database |
| `<project>/.tempest/` | Per-project, in-repo state: git worktrees and the Token Intelligence index (`.tempest/atlas/`) |

## RuntimeState shape

**File:** `src/lib/runtimeState.ts`

`RuntimeState` is the shape of the `"runtime"` preferences blob. Every field is optional from the database's point of view — missing keys fall back to defaults:

```typescript
export interface RuntimeState {
  settings: Partial<AppSettings>;
  keybindings: Partial<Record<ActionId, Shortcut | null>>;
  attribution: boolean;
  onboardingComplete: boolean;
  sessionOrder: string[];          // session ids in tab-bar order
  activeInstanceId: string | null; // id of the last focused session
  prompts: Array<{ id: string; title: string; body: string; enabled: boolean; isBuiltin: boolean }>;
  atlasProjects: Record<string, boolean>; // projectPath → indexed? (Token Intelligence decision)
  agentConfigs: Record<string, PerAgentConfig>; // agent id → per-agent launch defaults
  customAgents: RemotePatch[];    // user-added agents, merged over bundled+remote
  theme?: string;         // active theme name
  chatProvider?: string;  // last selected chat provider id
  chatModel?: string;     // last selected chat model id
}
```

Access is centralized in four functions:

| Function | Purpose |
|----------|---------|
| `loadAppState()` | Reads the `"runtime"` blob from `app_state` and merges it over defaults. Called once at boot |
| `getRuntimeState()` | Returns the current in-memory state |
| `setRuntimeState(patch)` | Merges the patch into memory and persists the full blob back to `app_state` |
| `getAgentConfig(id)` / `setAgentConfig(id, cfg)` | Synchronous accessors over the `agentConfigs` slice so the spawn path never needs a DB round-trip |

## Boot sequence

`src/main.tsx` hydrates every in-memory mirror from SQLite **in parallel before the first render**:

```typescript
await Promise.all([
  loadAppState(), loadSessions(), loadProjects(), loadRecents(), loadTabs(),
  terminalRendererPolicy.initialize(),
]);
refreshAgentRegistry(); // rebuild now that customAgents is hydrated
```

- `loadAppState` — loads the `"runtime"` preferences blob
- `loadSessions` / `loadProjects` — hydrate from the `db_load` snapshot (projects, branches, sessions)
- `loadRecents` / `loadTabs` — hydrate from `db_load_recents` and `db_load_tabs`
- `terminalRendererPolicy.initialize()` — decides WebGL vs. canvas rendering before the first terminal mounts

Only after all six resolve does React render, so no component ever sees a half-hydrated store.

## Store modules

All 24 store modules live in `src/store/`. Each is a singleton built on `useSyncExternalStore`: components subscribe through a `use*` hook and re-render only when their slice changes.

| Module | Purpose |
|--------|---------|
| `appSettings` | Terminal and app settings, merged over hardcoded defaults |
| `keybindings` | Custom keyboard shortcuts, merged over the built-in defaults |
| `sessionManager` | Singleton that watches PTY output, escape sequences, and terminal titles to detect when an agent finishes |
| `sessions` | Metadata for worktree and project-root sessions, mirrored from the `sessions` table |
| `openProjects` | Projects shown in the sidebar, backed by the `projects` table |
| `recents` | Recently opened projects, backed by the `recents` table |
| `tabs` | Non-terminal tabs (diff, preview, editor, thread), backed by the `tabs` table |
| `worktrees` | Runtime mirror of the per-project `.tempest/*` disk scan plus a git-repo hint; read by the mobile projector |
| `workState` | Per-session `idle` / `working` / `done` status |
| `nodeActivity` | Ephemeral activity state for workspace nodes |
| `messageQueue` | Per-session queue of messages shown in the UI popover |
| `automations` | Automation definitions and schedule state over the `automations` tables |
| `agentHooks` | Receiver for the `agent-hook` event; feeds precise agent lifecycle state into `sessionManager` |
| `agentAvailability` | Which agent CLIs are available on this machine |
| `prompts` | Builtin and custom prompts, persisted in the runtime blob |
| `attribution` | Whether the co-author attribution hook is enabled |
| `islandNotifs` | Notification feed for the island UI (permission requests, completions) |
| `quotas` | Polls `quota_read_all` on a five-minute cadence and exposes provider usage |
| `updates` | App update checks via the Tauri updater plugin |
| `threads` | Thread boards, backed by the `threads` tables |
| `threadMessages` | Messages within threads, backed by the `thread_messages` table |
| `mobilePairings` | Pairing state with the mobile companion |
| `mobileControlledSessions` | Sessions currently shared with the mobile companion |
| `reviewComments` | Review comment state for the diff and PR review surfaces |

## Ephemeral vs. persisted

| Layer | Examples | Fate |
|-------|----------|------|
| Memory-only | `workState`, `nodeActivity`, `messageQueue` | Rebuilt or discarded on restart |
| SQLite | `sessions`, `tabs`, `threads`, `threadMessages`, `automations`, `notes`, `recents`, `openProjects` | Survive restarts |
| Runtime blob | `settings`, `keybindings`, `prompts`, `agentConfigs`, `customAgents`, `theme` | Survive restarts inside `app_state` |

The Message Queue is deliberately **not** persisted: it is a short-lived handoff surface for typed-but-not-sent messages, and queueing stale text across restarts would surprise the user. Work state, likewise, is re-derived live from PTY output and agent hooks.

## Project settings and tempest.yml

Per-project security settings are edited in the Project Settings panel (`ProjectSettingsPanel/useProjectSettings.ts`) and grouped into seven sections:

| Group | Fields |
|-------|--------|
| `sandbox` | `mode: off \| monitor \| enforce` |
| `network` | `policy: permissive \| restrictive`, `allowHosts`, `blockHosts` |
| `filesystem` | `rwPaths`, `roPaths` |
| `permissions` | `allowSkipPermissions`, `allowRepoHooks` |
| `agents` | `permitted` (which agent CLIs may launch) |
| `database` | `isolationEnabled` |
| `resources` | `maxMemoryMb`, `maxProcesses`, `maxDiskWriteMb`, `cpuWeight` |

A project can also commit a `tempest.yml`. Because the file arrives with the code, it is merged in the **tightening direction only** (`clampSecurity` in `src/lib/tempestConfig.ts`): a repo can lock itself down further than the user's panel, never loosen it. Sandbox mode only escalates, blocklists only grow, allowlists only shrink, quotas only shrink. The config's `env` block is additionally filtered through a denylist of loader and DB-isolation variables (`PATH`, `NODE_OPTIONS`, `LD_PRELOAD`, `DATABASE_URL`, and similar), so a hostile repo cannot use environment variables for code execution. Full schema on the [tempest.yml](/tempest-yml) page.

## Migration notes

Earlier versions of Tempest persisted state in browser `localStorage`. That era is over: legacy keys were migrated into SQLite at startup and are no longer read. Current builds keep exactly three `localStorage` uses, all deliberate and all UI-local:

| Key | Used by | Purpose |
|-----|---------|---------|
| `tempest-github-token` | `PrDialog` | GitHub token for the PR dialog |
| `tempest:tasks-page:v1` | `TasksPage` | Task list filter state |
| `tempest-run-custom:{cwd}` | `RightSidebar` | Custom Run commands, per working directory |

Everything else — settings, sessions, tabs, threads, prompts, agent configs — belongs to `tempest.db` now.

## Example: reading and writing preferences

Stores read settings through the runtime state; a write persists synchronously to memory and asynchronously to SQLite:

```typescript
import { getRuntimeState, setRuntimeState } from "../lib/runtimeState";

const fontSize = getRuntimeState().settings.terminalFontSize ?? 13;
const theme = getRuntimeState().theme ?? "dark";

// Merge one patch; the whole blob is written back to app_state.
setRuntimeState({ theme: "noir" });
```

Under the hood this is two Tauri commands over the `app_state` table:

```typescript
import { invoke } from "@tauri-apps/api/core";

// Read every blob (returns [key, value] rows).
const rows = await invoke<[string, string][]>("db_load_app_state");
const state = JSON.parse(new Map(rows).get("runtime") ?? "{}");

// Write one blob back.
await invoke("db_set_app_state", {
  key: "runtime",
  value: JSON.stringify({ ...state, theme: "noir" }),
});
```
