# Tempest Architecture

Tempest is a desktop app for running many AI coding agents in parallel, each in its own isolated git worktree. This page describes how the system is put together: the Rust backend, the React frontend, the IPC layer between them, the worktree model, process isolation, database branching, and Token Intelligence.

## 1. High-Level Overview

Tempest splits responsibilities between a web-technology frontend and a native Rust backend, connected by Tauri's IPC:

```
┌──────────────────────────────────────────────────────────────────┐
│                    Frontend — React 19 / Vite                    │
│                                                                  │
│   Workspaces          xterm.js terminals      CodeMirror editor  │
│   Diff viewer         Git UI                  Threads canvas     │
└───────────────────────────────┬──────────────────────────────────┘
                                │
              Tauri IPC — invoke (request/response),
              Channels (PTY output streams), app.emit (events)
                                │
┌───────────────────────────────▼──────────────────────────────────┐
│                      Backend — Rust (src-tauri)                  │
│                                                                  │
│   PTY sessions (portable-pty)      Git subprocess operations     │
│   Worktree management              Hephaestus isolation          │
│   DB isolation (dbiso)             Atlas spawn / MCP config      │
│   SQLite persistence               Node bridge sidecars          │
└───────────────────────────────┬──────────────────────────────────┘
                                │
              ┌─────────────────┼──────────────────┐
              ▼                 ▼                  ▼
      Git worktrees        Atlas MCP daemon    Bridge sidecars
      under .tempest/      (one per project)   claude · codex ·
                                               opencode · gemini
                                               + cloudflared
                                               (mobile pairing)
```

The **frontend** owns UI logic and user interaction. The **backend** owns every OS-level operation: spawning processes, streaming PTY output, running git, managing worktrees, confining processes, and talking to Docker. Several side processes fan out from the backend: git worktrees under the project's `.tempest/` directory, one Atlas MCP daemon per indexed project, Node bridge sidecars for chat (`claude`, `codex`, `opencode`, `gemini`), and a `cloudflared` sidecar used for mobile pairing.

## 2. Repository & Process Model

Tempest is a **Tauri 2 + React 19** desktop application; frontend and backend versions are matched at **0.1.25**. A local Windows build produces NSIS and MSI installers (bundle targets `["nsis", "msi"]`); released macOS and Linux artifacts are built in CI.

The Rust side is a Cargo **workspace**:

| Crate | Purpose |
|-------|---------|
| `tempest` (root, library name `tempest_lib`) | The application crate — all backend modules below. |
| `crates/hephaestus` | Process isolation SDK. |
| `crates/dbiso` | Docker database branching. |
| `crates/hephaestus-driver` | Optional Windows kernel driver. Excluded from the workspace; built separately with the Windows Driver Kit (WDK). |

The root crate's modules:

| File | Role |
|------|------|
| `lib.rs` | ~5,400 lines. PTY sessions, git operations, worktrees, Atlas glue, zen windows, SQLite init. |
| `tasks.rs` | GitHub and Linear tasks. |
| `automations.rs` | Automation scheduler. |
| `pairing_relay.rs` | Mobile WebSocket router plus cloudflared tunnel management. |
| `canvas_mcp.rs` | In-binary MCP stdio server, launched with `--canvas-mcp`. |
| `claude_bridge.rs` | Chat bridge sidecar spawning. |
| `warp_bridge.rs` | Experimental Warp chat backend. |
| `agent_hooks.rs` | Loopback HTTP receiver for agent lifecycle hooks. |
| `quota/*` | Per-provider usage readers: claude, codex, grok, cursor, copilot. |
| `tasks_store.rs` | Task store with a 60 s TTL cache. |
| `node_ingest.rs` | File, URL, and media extraction. |
| `extensions.rs` | Extension support. |
| `notes.rs` | Notes. |
| `secrets.rs` | OS keyring access (service `tempest-byok`). |
| `service_proxy.rs` | Reverse proxy serving `<slug>.localhost` on port 7000. |

| `wsl.rs` | WSL integration. |

**144 Tauri commands** are registered in `generate_handler!`. Every command is documented in [Tauri commands](/internals/tauri-commands), and the persisted state model is described in [App state internals](/internals/state).

## 3. IPC Communication

The frontend and backend talk over three Tauri mechanisms:

1. **`invoke`** — request/response. Every command returns `Result<T, String>`; errors surface in the frontend as strings.
2. **`Channel<PtyOutputPayload>`** — a typed channel passed into a command so the backend can stream results back. PTY output is streamed this way, batched in roughly **16 ms / 64 KiB** windows.
3. **`app.emit`** — app-wide event broadcasts.

Emitted events:

| Event | Emitted when |
|-------|--------------|
| `atlas:log` | Atlas indexing progress |
| `atlas:model-download` | Semantic model download progress |
| `db:log` | Database-branch (dbiso) operation logs |
| `automation:dispatch` | An automation is due to run |
| `agent-hook` | An agent lifecycle hook fired |
| `run:{id}` | Per-automation-run progress (run id in the name) |
| `hook:{token}` | Per-hook delivery (token in the name) |

PTY output is deliberately **not** one of these broadcasts — it streams over the per-session `Channel` passed to `create_pty_session`, so each terminal only receives its own data.

A frontend `invoke` that streams PTY output through a `Channel`:

```typescript
import { invoke, Channel } from "@tauri-apps/api/core";

type PtyOutputPayload = { session_id: string; data: string };

const onEvent = new Channel<PtyOutputPayload>();
onEvent.onmessage = (payload) => terminal.write(payload.data);

await invoke("create_pty_session", {
  sessionId: "s-fix-auth",
  cwd: "D:/code/my-app/.tempest/fix-auth",
  rows: 30,
  cols: 120,
  onEvent,
});
```

The Rust side of the same flow:

```rust
// Stream a PTY chunk to the frontend over the session's channel.
on_event
    .send(PtyOutputPayload {
        session_id: sid.clone(),
        data: String::from_utf8_lossy(&buf[..n]).to_string(),
    })
    .ok();

// Broadcast an app-wide event.
app.emit("atlas:log", serde_json::json!({ "path": &project_path, "line": line }))?;
```

## 4. Persistence (SQLite)

All persistence lives in a single SQLite database at `<app-data-dir>/tempest.db` (app identifier `com.user.tempest`) with **16 tables**:

| Tables | What they hold |
|--------|----------------|
| `projects`, `branches` | Opened projects and their branch metadata |
| `sessions` | Worktree sessions |
| `layouts`, `layout_nodes` | Saved pane layouts |
| `recents`, `tabs` | Recent projects and the persisted tab bar |
| `app_state` | The preferences blob (below) |
| `threads`, `thread_nodes`, `thread_messages`, `thread_edges` | Threads canvas and chat history |
| `automations`, `automation_runs`, `automation_prompt_versions` | Automations, their runs, and per-automation prompt versions |
| `notes` | Notes |

App preferences persist as a **single JSON blob row** in `app_state` under the key `"runtime"`, read and written by the `db_load_app_state` / `db_set_app_state` commands. The frontend hydrates it into a `RuntimeState` object containing `settings`, `keybindings`, `attribution`, `onboardingComplete`, `sessionOrder`, `activeInstanceId`, `prompts`, `atlasProjects`, `agentConfigs`, `customAgents`, `theme`, `chatProvider`, and `chatModel`.

Boot hydration happens in `src/main.tsx`, which runs `loadAppState`, `loadSessions`, `loadProjects`, `loadRecents`, and `loadTabs` **in parallel before the first render**.

<Callout type="info">
There is no `runtime-state.json` and no localStorage session persistence. Legacy localStorage data was migrated into SQLite; new code reads and writes only the database and React stores.
</Callout>

Other on-disk locations:

| Location | Contents |
|----------|----------|
| `~/.tempest/dbiso.db` | Database-branch registry |
| `~/.tempest/hooks/` | Agent hook scripts plus `endpoint.env` / `endpoint.cmd` |
| `<app-data-dir>/atlas-daemons.json` | Atlas daemon PID map |
| OS keyring (service `tempest-byok`) | BYOK API keys |
| `<project>/.tempest/` | Worktrees and the Atlas index |
| Project root | Agent MCP config files (gitignored) |

## 5. The Worktree Model

Every agent session runs in a **git worktree** at `<project>/.tempest/<name>` — slashes in a name map to `-`. Each worktree is a full checkout with its own branch, backed by the shared `.git` directory, so agents never touch each other's files or the main working tree.

### Creation flow

<Steps>
  <Step title="Claim from the warm pool when possible">
    Tempest keeps a warm pool of **3 pre-created slots** with a **5-minute TTL**, staged in `.tempest/.warm-<uuid8>` on branch `tempest-prep/<uuid8>`. A new session claims a warm slot when one is available, which makes opening a workspace near-instant.
  </Step>
  <Step title="Fall back to a fresh worktree">
    On a pool miss, Tempest runs `git worktree add --no-checkout` and then materializes the checkout.
  </Step>
  <Step title="Copy env files">
    `.env`, `.env.local`, `.env.development`, and `.env.production` are copied from the project root so agents can read them.
  </Step>
  <Step title="Link dependency directories">
    `node_modules` and `.venv` are linked, not copied — a Windows junction on Windows, a Unix symlink elsewhere. This avoids copying hundreds of megabytes per session.
  </Step>
  <Step title="Persist the child PID">
    The shell's PID is written to `<worktree>/.tempest-pid`, kept out of `git status` via `.git/worktrees/<name>/info/exclude`. This lets Tempest kill orphaned processes after an app restart.
  </Step>
  <Step title="Validate">
    An empty tree (only `.git/`) is rejected, so an agent never starts in a blank checkout.
  </Step>
</Steps>

### Cleanup flow

`close_pty_session` tears a session down in order: lifecycle job, then `isolate destroy`, then DB-branch delete, then a `taskkill` / `kill` sweep. After the processes are gone:

1. Junctions and symlinks are removed **before** `remove_dir_all` — otherwise the recursive delete follows the junction into the real `node_modules`.
2. Removal retries in a loop on Windows while directory handles drain.
3. `git worktree prune` clears dangling git metadata.

## 6. Agent Spawn Pipeline

The frontend pre-assembles the agent invocation and calls `create_pty_session` with:

- `session_id`, `cwd`, `rows`, `cols`
- optional `command` and `args` (a plain shell session omits both)
- optional `sandbox` (a `SandboxSpec`) and `policy` (a `SessionPolicy`)
- `db_isolation`, `env` (the `tempest.yml` env map), `worktree_add`
- `on_event` — the output channel

### Launch policy gate

Before any resource is acquired, the backend vets the launch: the agent must be in the project's `permitted_agents`, and if `allow_skip_permissions` is `false`, any skip-permission flag found in `args` is refused.

### Shell and quoting

The frontend sends arguments as a list; **Rust shell-quotes them** — doubling single quotes for PowerShell on Windows, POSIX `'\''` escaping elsewhere. The shell is resolved once and cached:

- **Windows**: probe `pwsh`, falling back to `powershell.exe`, spawned with `-NoLogo -NoExit -Command`.
- **Unix**: use `$SHELL` (falling back to `/bin/bash`), spawned with `-lic "<invocation>; exec $SHELL -il"` so the agent runs in a login shell that stays open afterwards.

### Environment

`TERM=xterm-256color` is set on non-Windows hosts. A project's [tempest.yml](/tempest-yml) can contribute extra environment variables through the `env` map, but a **denylist is enforced** — `PATH`, `NODE_OPTIONS`, `LD_PRELOAD`, `DYLD_*`, `PYTHONPATH`, `DATABASE_URL`, `PG*`, and similar names are rejected. Database-isolation variables are written into the live shell **after** spawn, not at spawn. See [Agents](/agents/supported) for the bundled agents and their launch defaults.

### MCP config files

When Token Intelligence indexes a project, Tempest writes MCP config files so every supported agent CLI finds the Atlas server:

- `.mcp.json` — read by Claude Code, Cline, Roo, Zed, and Windsurf
- `.cursor/mcp.json`
- `.gemini/settings.json`
- `.kiro/settings/mcp.json`
- `opencode.jsonc`

All of these are gitignored. Codex gets a global entry in `~/.codex/config.toml` under `[mcp_servers.atlas]`, and Goose gets `~/.config/goose/profiles.yaml`.

### Output pump

A reader thread per PTY batches output into the `Channel` (~16 ms / 64 KiB windows), keeping the frontend terminal live without flooding IPC.

## 7. Hephaestus: Process Isolation

Hephaestus (`crates/hephaestus`) is Tempest's process isolation SDK. Each session can carry a `SandboxSpec`:

<Properties>
  <Property name="mode" value="Isolation mode: off, monitor, enforce, or lifecycle (default: off)" />
  <Property name="allowed_hosts / block_hosts" value="Hostname allow and deny patterns for the network policy engine" />
  <Property name="network_default_allow" value="true mirrors the permissive policy; false mirrors the restrictive policy" />
  <Property name="rw_paths / ro_paths" value="Paths mounted read-write and read-only inside the sandbox" />
  <Property name="resources" value="max_memory_mb, max_processes, max_disk_write_mb, cpu_weight" />
</Properties>

### Platform enforcement

<Tabs>
  <Tab title="Windows">
    - **Job Objects** with `KILL_ON_JOB_CLOSE`, with optional memory and process caps plus CPU rate weight.
    - An **ETW ProcessWatcher** (Kernel-Process provider) assigns brokered descendants into the job. This requires admin or Performance Log Users membership and is **silently skipped otherwise**.
    - An optional kernel driver (`\\.\HephaestusDriver`, IOCTLs `0x800`, `0x801`, `0x802`).
    - Every unsandboxed session still gets a **lifecycle job**: kill-on-close plus ETW tracking plus a teardown sweep.
    - Network policy is env-var proxy injection — a policy filter, **not** a containment boundary.
  </Tab>
  <Tab title="macOS">
    Seatbelt SBPL profiles via `sandbox-exec`. In enforce mode the profile denies by default: read-only system paths, a read-write workspace, and network-outbound **only** to the in-process proxy on `127.0.0.1`.
  </Tab>
  <Tab title="Linux">
    bubblewrap with `--unshare-pid --die-with-parent --unshare-net --dev /dev --proc /proc` plus binds. cgroups and seccomp are **not** implemented.
  </Tab>
</Tabs>

<Warning>
Enforcement is honest about its limits: resource limits are enforced on Windows only, `max_disk_write_mb` is accepted but not enforced anywhere, and Windows network policy filters cooperating processes rather than containing them.
</Warning>

### Network policy engine

A network policy engine runs as an **in-process HTTPS CONNECT proxy** (`proxy.rs`). Hostnames are matched against `HostPattern` entries — `**.x` suffix, `*.x` subdomain, or exact match — and a blocked match always beats an allowed one.

### Configuration

The default mode is `off`. Sandboxing is configured per project through Project Settings (Security group) or [tempest.yml](/tempest-yml), with a **tightened-only merge** — a project can make its sandbox stricter than the default, never looser. See [Security](/security/overview).

## 8. Database Branches (dbiso)

`crates/dbiso` gives each session an isolated PostgreSQL **16** database, built from the project's real database via the bollard Docker API (image `postgres:16-alpine`).

### Snapshot methods

- **`basebackup`** — `pg_basebackup` against the source database.
- **`pgdump`** — logical dump; forced for pooler hosts such as `*.pooler.supabase.com`.
- **Schema-only** — structure without data.

### Build flow

<Steps>
  <Step title="Stage">
    A staging container `tempest-staging-<uuid8>` runs with `PGDATA=/pgdata` — deliberately not the image's VOLUME path, so the commit includes the data.
  </Step>
  <Step title="Import">
    `initdb`, then import the snapshot.
  </Step>
  <Step title="Prewarm">
    `ANALYZE; CHECKPOINT` so the first queries on a branch are fast.
  </Step>
  <Step title="Tune">
    Write a tuned `postgresql.auto.conf`: `fsync=off`, `synchronous_commit=off`, `full_page_writes=off`, `wal_level=minimal`, `max_wal_senders=0`, `shared_buffers=256MB`.
  </Step>
  <Step title="Commit">
    Commit the container as image `tempest-db-base-<project-slug>-<uuid>`.
  </Step>
</Steps>

### Branching and delivery

A branch runs as container `tempest-<branch_name>`, with the branch name derived from the session id (`tempest-<8 chars>`). The host port is the first free port in `15432..=65000`, bound to `127.0.0.1`, and readiness polls `pg_isready` for up to 15 s.

On success, `DATABASE_URL`, `PGHOST`, `PGPORT`, `PGUSER`, and `PGDATABASE` are written into the live session shell — PowerShell `$env:` or POSIX `export` — **before the agent invocation runs**, so the agent talks to the branch without any manual setup.

### Registry and lifecycle

The registry at `~/.tempest/dbiso.db` tracks `base_images` and `branches`. Branches are deleted when their session closes, and an orphan sweep runs at startup. The Tauri commands are `db_check_docker`, `db_check_ready`, `db_build`, `db_list_branches`, and `db_sweep_orphans`. See [Database branches](/database-branches/overview).

## 9. Token Intelligence (Atlas)

Atlas is Tempest's code-intelligence engine, shipped as the npm package **`@usetempest/atlas`** (v1.3.x, MIT). Its postinstall script, `scripts/install-atlas.mjs`, stages it into `src-tauri/resources/atlas/`, pruning to the current platform and refusing to stage an incomplete dist.

- **Index database**: `<project>/.tempest/atlas/atlas.db` (SQLite, WAL mode).
- **Indexing**: `start_atlas_index` spawns `node <atlas>/dist/mcp/server-entry.js --init --path <project>`, adding `--semantic --model-cache` when semantic search is enabled. The semantic model is a one-time ~25 MB MiniLM download via `download_atlas_model`.
- **Daemon**: one per project, managed by `start_atlas_daemon` / `stop_atlas_daemon` and tracked in `atlas-daemons.json`.
- **Agent access**: agents reach the daemon through the MCP config files written at index time (see the spawn pipeline above).

The default MCP surface is `atlas_explore`, `atlas_assets`, `atlas_asset_content`, and `atlas_semantic_search`. The legacy tools — `node`, `search`, `callers`, `callees`, `impact`, `files`, `status` — remain callable through the `ATLAS_MCP_TOOLS` environment variable.

The Tempest UI reads the same graph through `get_atlas_graph` / `atlas_query` to power the Knowledge Base page. Separately, `write_canvas_mcp_config` registers a `tempest-canvas` MCP server that is served by **Tempest's own binary** (launched with `--canvas-mcp`). See [Token Intelligence](/token-intelligence/overview) and [Knowledge Base](/knowledge-base/overview).

## 10. Chat & Bridge Sidecars

Chat nodes on the Threads canvas have three backends:

1. **BYOK** — the Vercel AI SDK's `streamChat` runs in the frontend against 9 providers, using keys from the OS keyring.
2. **CLI bridges** — Node sidecars at `resources/{claude,codex,opencode,gemini}-bridge/bridge.mjs`, spawned by `claude_stream_start` and streaming NDJSON over `claude://{stream_id}` channels. The Claude bridge drives Claude Code through `@anthropic-ai/claude-agent-sdk`.
3. **Warp (experimental)** — the `warp_chat` / `warp_model_info` Rust commands over the `warpllm` 0.4 crate. Off by default.

See [Threads](/threads/overview) for the canvas itself.

## 11. Mobile Pairing & Remote

The mobile relay is a Rust WebSocket router in `pairing_relay.rs`. The transport is selected by the `TEMPEST_MOBILE_TRANSPORT` environment variable:

- **`lan`** (default) — binds `0.0.0.0:0` and discovers the LAN IP via a UDP route probe.
- **`tunnel`** — a cloudflared quick-tunnel sidecar exposes `wss://<random>.trycloudflare.com/ws`, with readiness polled via the metrics `/ready` endpoint.

`start_pairing_relay` / `stop_pairing_relay` return a `TunnelInfo`:

<Properties>
  <Property name="wss_url" value="URL embedded in the pairing QR code" />
  <Property name="local_port" value="Local port the router bound to (diagnostic)" />
  <Property name="transport" value="Which transport served the URL: lan or tunnel" />
</Properties>

Relay behavior: the desktop always dials its own router via loopback; each session supports exactly one laptop plus one phone; frames are forwarded blindly and bidirectionally, with `__relay` control frames and a `__ping` / `__pong` keepalive every ~25 s.

**End-to-end encryption lives in TypeScript**, not in the relay:

- **`@tempest/crypto`** — X25519 keypairs, nacl secretbox, session key via `box.before`, 8-hex fingerprint.
- **`@tempest/core`** — wire types and RPC methods: `session.list/get/open/close/hop`, `queue.*`, `agent.send/interrupt/resize`, `permission.list/decide`, `protocol.hello`, `push.register`; server events such as `session.updated`, `agent.output`, and `permission.pending`.
- **`@tempest/transport`** — `RpcPeer`, `wsChannel`, E2EE frames `{n, c}`, exponential backoff from 500 ms to 30 s.

`apps/relay` is a Cloudflare Worker + Durable Object alternative router kept for a future switch — it is not the live path. `apps/mobile` is the Expo companion app. See [Mobile](/mobile/overview).

## 12. Automations

Automations live in the SQLite tables described above. A Rust scheduler thread ticks every **60 s** and emits `automation:dispatch` for due automations. The **frontend** then runs the headless agent: it builds the invocation from the agent manifest's `printArgs` (plus `modelArgs` and `autoApproveArgs`) and runs it in a PTY with `TEMPEST_SESSION=<runId>` in the environment.

Run statuses move through `dispatching` → `dispatched` → `succeeded` or `dispatch_failed`. Prompt versions are stored per automation, so schedule edits never lose the prompt that produced a given run. See [Automations](/automations/overview).

## 13. Frontend Architecture

The frontend is React 19 on Vite (dev server on port 1420), 250+ TS/TSX files. There is **no Redux or Zustand**: 24 store modules in `src/store/` are built on `useSyncExternalStore` singletons. Notable stores include `sessions`, `sessionManager`, `workState`, `messageQueue`, `automations`, `tabs`, `threads`, `threadMessages`, `quotas`, `islandNotifs`, `updates`, `agentAvailability`, `mobilePairings`, `mobileControlledSessions`, and more.

### sessionManager

`sessionManager` owns PTY channels, scrollback ring buffers (**2 MB attached, 128 KB detached**), and **work-done detection**:

- **Precise hooks** (default): the loopback agent-hook receiver plus 8 adapters.
- **Fallback PTY heuristics**: OSC sequences `1337`, `9;4`, `9`, `133`, and `777`, title classification, DEC `2004`/`1049`, the Claude permission fingerprint, and timers — 5 s quiet, 300 ms dead zone, 12 s ceiling, 200-byte gate.

### Panes and the Threads canvas

Sessions live either in the top tab bar or in a binary split tree (`lib/paneLayout.ts`). The Threads canvas (`ThreadsView`) supports node kinds `chat`, `text`, `agent`, `terminal`, `file`, `image`, `media`, `site`, and `collapsed`, laid out with cytoscape-fcose in a worker. See [Threads](/threads/overview) and [Agents](/agents/overview).

### Terminal rendering

A pool of **6 WebGL contexts** serves xterm, with a canvas fallback, WSL-aware.

### Directory purpose summary

| Directory | Purpose |
|-----------|---------|
| `src/` | React 19 frontend: components, stores, libs, themes, workers, extensions |
| `src-tauri/` | Rust backend: `lib.rs` and its modules, the Hephaestus, dbiso, and driver crates, bundled resources and binaries |
| `<project>/.tempest/` | Per-project runtime area: worktrees, warm-pool staging, Atlas index database |
| `~/.tempest/` | Machine-global state: dbiso registry and agent hook scripts (the Atlas daemon PID map lives in the app data dir) |
| App data dir | `tempest.db` SQLite database (identifier `com.user.tempest`) |
| Agent MCP configs | `.mcp.json`, `.cursor/mcp.json`, `.gemini/settings.json`, `.kiro/settings/mcp.json`, `opencode.jsonc` in the project root (gitignored) |

## Summary

Tempest pairs a React 19 frontend with a Tauri 2 Rust backend over three IPC mechanisms — `invoke` for request/response, `Channel` for streamed PTY output, and `app.emit` for events — with all persistence in a single SQLite database. Agents run in git worktrees under `.tempest/`, warmed by a small pool and torn down through a careful junction-aware cleanup sequence. Hephaestus confines each session per platform with honestly documented limits, dbiso gives each agent a disposable PostgreSQL branch, and Atlas puts a semantic code graph in front of every agent through MCP config files. Bridges, the mobile relay, and automations build on the same primitives, so one process model — spawn, confine, stream, persist, clean up — covers everything Tempest does.
